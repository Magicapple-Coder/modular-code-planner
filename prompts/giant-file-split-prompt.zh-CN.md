# 巨型代码文件企业级拆分 · 万能提示词

> **使用方法**：把下方 `▼▼▼` 与 `▲▲▲` 之间的整段提示词复制给 AI，先填好「任务信息」里的 4 个空（文件路径、语言/框架、验证命令、行数上限），再附上你的代码或让它自己读项目。
> 提示词强制 AI「先出方案、确认后再动手」，并禁止它用「删测试 / 注释报错代码 / 放宽类型检查」的方式伪造通过。
> 配套 Skill：`modular-code-planner`（写新项目时从源头做模块规划）+ `scripts/check_file_sizes.py`（行数体检）。

---

## ▼▼▼ 复制以下全部内容 ▼▼▼

你是一名资深软件架构师。现在要把我项目中已经膨胀失控的巨型代码文件，按企业生产级标准**安全**拆分为模块化结构。安全性优先于速度：宁可停下问我，也不要猜着改。

### 一、任务信息

- 待拆分目标（文件或目录路径）：{{例如 src/main.py，或「整个项目，重点是 app.js」}}
- 语言 / 框架 / 运行环境：{{例如 Python 3.11 + FastAPI / React + TypeScript / Go 1.22}}
- 启动、测试、构建、类型检查命令：{{例如 pytest -q、npm test、npm run build、npx tsc --noEmit；没有测试请明确说没有}}
- 单文件行数上限：软上限 300 行、硬上限 500 行（我团队另有规范则以我的为准）
- 版本状态：我已提交/备份当前代码；若当前工作区有未提交改动，请先提醒我，不要自己提交或回滚
- 额外约束（可选）：{{例如必须保持 Python 3.9 兼容、不能新增第三方依赖、必须先合并某分支}}

### 二、不可违背的约束（优先级高于一切）

1. **行为完全等价**：拆分只做代码的位置移动和 import/引用路径调整。严禁借拆分之名修改业务逻辑、重写算法、更换库、改动输入输出、顺手「优化」或修 bug。发现疑似 bug 或设计问题，只记录到问题清单并向我报告，由我决定是否另开任务处理。
2. **先方案、后动手**：在我明确确认拆分方案之前，禁止创建、修改、删除任何代码文件，第一步只允许只读分析（读文件、全局搜索、运行只读命令）。
3. **改动范围最小**：只允许改动目标文件及其直接引用方。禁止格式化整仓、禁止顺手重构无关文件、禁止重命名无关符号、禁止改动与本任务无关的配置。
4. **小步迁移、步步可验证**：一次只迁移一个内聚职责。每完成一步立即运行验证命令，并向我报告四项：**本步改动的文件清单、新增/删除行数、实际执行的命令、命令的真实输出**。验证不通过先修复或回滚本步，不允许带着失败继续下一步。
5. **禁止用任何手段伪造通过**（违反即视为任务失败，我会以此验收）：
   - 禁止删除、跳过或弱化既有测试（`skip`、`xfail`、`@Ignore`、只留 `.only`、把断言注释掉）；
   - 禁止用注释掉报错代码、`try/except: pass`、空 catch 来掩盖问题；
   - 禁止放宽类型检查（`any`、`cast`、`# type: ignore`、`eslint-disable`、降低 tsconfig `strict`、关闭 lint 规则）；
   - 禁止为了让编译通过而保留两份实现、留下未删的旧代码或临时兼容分支；
   - 禁止修改验证命令本身使其更容易通过。
6. **公开接口保持兼容**：拆分后外部对原文件的引用要么全部同步更新，要么在原文件保留薄聚合层（re-export）做过渡。由你在方案中给出选择和理由，并说明依据是哪些引用方，不得让外部调用方悄悄失效。
7. **不丢代码、不留死代码**：迁移前全局搜索确认每个符号的引用方；重复代码提取为公共模块，确认无引用后才删除原代码；不理解的代码先问我，禁止删除。
8. **依赖方向单向**：入口层 → 业务层 → 领域/数据层 → 公共工具，禁止出现循环依赖；两个模块必须互相引用时，把共享的类型/接口抽到第三方模块。
9. **达到行数标准**：拆分后每个文件单一职责、命名清晰可预测，且不超过上述行数上限；确有特殊情况无法达到，必须在方案中单独说明理由，不得静默交付超长文件。
10. **不确定就停**：遇到方案没预料到的隐藏耦合、动态引用或行为不一致，立即暂停向我说明，不要自行发挥。

### 三、严格按四个阶段执行

**阶段 1 · 只读盘点（不改任何代码）**

先运行一遍全部验证命令，记录**基线结果**（含既有失败项，避免把它算成拆分引入的问题），然后完整通读目标文件及其直接关联文件，输出：

1. **职责清单**：该文件实际承担了哪几个相互独立的职责，每个职责对应哪些函数/类和大致行号区间；
2. **符号清单**：全部顶层函数、类、常量、类型，各自被谁调用（文件内部 / 跨文件 / 对外公开）；
3. **依赖清单**：所有 import 分别服务于哪个职责，以及模块级全局状态、单例、导入即执行的副作用；
4. **对外契约**：项目中哪些文件引用了目标文件、用到了哪些符号（这是必须兼容的公开面）；
5. **隐藏耦合**，逐项排查并明确给出结论：
   - 执行顺序依赖、共享可变变量、隐式数据格式约定；
   - **字符串 / 动态引用**：`getattr`、`importlib`、反射、依赖注入容器与组件扫描、路由字符串、模板引用、配置里的类路径、`entry_points`、序列化/反序列化路径；
   - 注册表与装饰器自动收集（插件、路由、ORM 模型、事件订阅者）；
   - monkey patch 与运行时替换；
   - 相对路径、`__file__` 相对定位、资源内嵌（如 Go `embed`）。
6. **代码体检**：运行 `check_file_sizes.py` 或等价手段，列出项目中所有超阈值文件及行数 Top 榜。

阶段 1 结束时暂停，等我确认清单完整后再进入阶段 2。

**阶段 2 · 拆分方案（输出后暂停，等我确认）**

1. 目标目录树，精确到文件；每个文件用一句话说明单一职责，并给出预估行数；
2. 符号迁移映射表：每个函数/类/常量「从哪里 → 到哪里」；
3. 公开接口兼容策略（全量更新 import / 保留 re-export 过渡层 / 兼容包装），说明选择理由与依据的引用方清单；
4. 模块依赖关系图或列表，说明如何避免循环依赖；
5. 自底向上的迁移步骤序列，保证每一步之后项目都处于可运行状态；
6. 每一步的验证方式（具体命令，不要写「运行测试」这种泛指）；
7. 拆分前后的行数对比预估；
8. 你建议**不要拆**的部分及理由（若有）；
9. 风险清单：哪些步骤最可能失败、失败时的回退点是什么。

方案经我确认或按我的意见修改后，才允许进入阶段 3。

**阶段 3 · 分步迁移**

1. 按方案自底向上执行：先建不依赖其他新模块的底层文件（类型、纯工具、常量），再逐层向上，最后改入口；
2. 一次一个职责：移动代码 → 修正引用 → 删除原位重复代码 → 运行验证 → 报告（文件清单 / 行数变化 / 命令 / 真实输出），然后再做下一步；
3. 以「移动」为主，函数体尽量原样搬迁；确需改名单独成步，不与移动混在一起；
4. 每完成一组步骤建立一个可回滚点（建议一次 commit，说明写清步骤号）；不要替我执行 git 提交或回滚，除非我明确要求；
5. 遇到方案没预料到的隐藏耦合，立即暂停并向我说明、更新方案，不硬迁、不猜。

**阶段 4 · 验收与交付报告**

1. 运行全部测试、类型检查、lint、构建，并实际启动/跑通关键路径（不只是单测绿）；
2. 统计拆分后每个文件的行数，确认全部低于上限，列出最终目录结构；
3. 检查无循环依赖、无重复定义、无死代码残留、无未使用 import，并确认以下位置不再指向旧路径：文档、README、脚本、CI/构建配置、部署配置；
4. 输出交付报告：
   - 新结构说明；
   - 迁移映射表（实际执行结果，并与方案对比，标出偏差及原因）；
   - 每步验证命令与结果；
   - **「拆分前后对外行为等价」的声明**，说明依据（测试覆盖范围 + 逐符号核对），并如实标注未被测试覆盖的部分；
   - 遗留问题清单（含拆分中发现的疑似 bug，注明「未修改」）；
   - 行数前后对比表。

### 四、输出与沟通要求

- 每个阶段开始时先用一句话说明本阶段要做什么；阶段产物用标题分节，映射关系用表格呈现。
- 信息不足或存在歧义时先向我提问，不要自行假设关键行为。
- 如果项目没有任何测试，请在阶段 1 先指出风险，并为关键路径补**最小特征测试**（只锁定现有输入输出行为，不得断言「应该是什么」，不得改动被测代码）后再拆分。
- 全程使用与我相同的语言，代码注释和命名遵循项目既有风格。
- 若某一步无法在合理时间内完成，暂停并汇报当前状态，不要长时间沉默或跳过失败步骤。

现在开始：先确认你已理解以上全部约束（逐条复述你怎么理解第 5 条和第 10 条），然后进入阶段 1 对目标文件做只读盘点。

## 配套使用建议

1. **第一次用**：让 AI 停在阶段 2。你重点审两样东西——「目录树」和「符号迁移映射表」，职责划分合理再放行。不要在这一步省时间。
2. **超大文件（>1500 行）**：在任务信息里补一句「每次只迁移一个职责后暂停，等我说继续再进行下一步」，控制节奏。
3. **没测试的项目**：提示词已要求先补特征测试，这是安全拆分的底线，不建议省。宁可不拆，也不要没有安全网地拆。
4. **想调整严格程度**：改「任务信息」里的行数上限即可。前端组件类文件可放宽到软 400 / 硬 600；强类型后端逻辑建议收紧到软 200 / 硬 400；入口文件一律目标 ≤100 行。
5. **验收时看什么**：不要只看「测试通过」。重点看阶段 3 每步报告里的「改动的文件清单」——如果某个步骤改了方案里没提到的文件，就是范围失控的信号；如果测试数量在拆分后变少了，直接打回。
6. **配套工具**：
   - `modular-code-planner` Skill：写新项目时先从源头做模块规划，避免边写边膨胀；也可随时对现有项目跑行数体检。
   - `scripts/check_file_sizes.py`：拆分前后各跑一次对比行数，脚本退出码为 1 表示仍有超硬阈值文件。
7. **拆分完成不等于结束**：把「为什么这样分」写进项目的 `CONTRIBUTING.md` 或架构说明里，否则三个月后新代码会重新长回巨型文件。
