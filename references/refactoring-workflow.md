# 巨型文件拆分 · 五阶段工作流

供 `modular-code-planner` 工作流 C 使用。**开始动手前完整读取本文件。**

铁律：**行为完全等价**——拆分只做位置移动与 import 调整。发现 bug 或设计问题只记录、不修。

---

## 阶段 0 · 冻结行为（安全网）

1. 确认版本状态：代码已提交/已备份，用户随时可回滚。未提交则先提醒用户提交。
2. 确认验证命令：测试、类型检查、lint、构建、启动。**先运行一次，记录基线结果**（含已知失败项，避免后续把既有失败误判为本次拆分引入）。
3. 若无任何测试：
   - 明确告知风险（无安全网的拆分不可验证）；
   - 为将被拆分的文件所覆盖的关键路径补**最小特征测试**：锁定现有输入输出行为，不断言「应该是什么」；
   - 测试本身不得改动被测代码（若被测代码不可测，先如实报告并请用户决策）。

**出口条件**：基线验证命令已运行并记录结果。未满足不得进入阶段 1。

---

## 阶段 1 · 只读盘点（禁止任何写操作）

完整通读目标文件及其直接关联文件。允许：读文件、全局搜索、运行只读命令。禁止：创建/修改/删除文件、格式化、批量重命名。

输出五份清单：

1. **职责清单**：该文件实际承担哪几个相互独立的职责，每个职责对应哪些函数/类及行号区间。
2. **符号清单**：全部顶层函数、类、常量、类型，各自被谁调用（文件内部 / 跨文件 / 对外公开）。
3. **依赖清单**：每个 import 服务于哪个职责；模块级全局状态、单例、导入即执行的副作用。
4. **对外契约**：项目中哪些文件引用了目标文件、用到了哪些符号——这是必须兼容的公开面。
5. **隐藏耦合**，逐项排查：
   - 执行顺序依赖、共享可变变量、隐式数据格式约定；
   - **字符串/动态引用**：`getattr`、`importlib`、反射、DI 容器/组件扫描、路由字符串、模板引用、序列化路径、配置里的类路径、`entry_points`；
   - 注册表/装饰器自动收集（插件、路由、ORM 模型、事件订阅者）；
   - monkey patch / 运行时替换；
   - 相对路径、`__file__` 相对定位、`embed` 资源引用。

**出口条件**：五份清单齐全，隐藏耦合有明确结论或明确标注「未发现，已排查方式为 X」。

---

## 阶段 2 · 拆分方案（输出后暂停，等用户确认）

必须包含：

1. **目标目录树**，精确到文件；每个文件一句话职责 + 预估行数；
2. **符号迁移映射表**：每个函数/类/常量「从哪 → 到哪」；
3. **公开接口兼容策略**：全量更新 import / 保留 re-export 过渡层 / 兼容包装。给出选择与理由，并明确声明「所选策略下外部调用方不会失效，依据是……」（引用阶段 1 的对外契约清单）；
4. **模块依赖关系图或列表**，说明如何避免循环依赖；
5. **自底向上的迁移步骤序列**：每一步之后项目都处于可运行状态，明确「先建哪个文件」；
6. **每一步的验证方式**：具体命令，不是「运行测试」这种泛指；
7. **拆分前后行数对比预估**；
8. **不拆的部分及理由**（若有）；
9. **风险清单**：哪些步骤最可能失败、失败时的回退点。

> **用户明确确认前，禁止创建、修改、删除任何代码文件。** 用户提出修改意见时，更新方案后再次确认。

---

## 阶段 3 · 分步迁移

1. **自底向上**：先建不依赖其他新模块的底层文件（类型、纯工具、常量），再逐层向上，最后改入口。
2. **一次一个职责**：移动代码 → 修正引用 → 删除原位重复代码 → 运行该步验证命令 → 报告 → 再做下一步。
   - 报告内容固定包含：本步改动的文件清单、新增/删除行数、验证命令与真实输出、是否与预期一致。
3. **以「移动」为主**：函数体尽量原样搬迁；确需改名单独成步，不与移动混在一起。
4. **每完成一个阶段（或一组步骤）建立回滚点**：建议一次 commit，commit message 写明步骤号。
5. **遇到方案未预料的隐藏耦合**：立即暂停，向用户说明现象与影响，更新方案并重新确认，**不硬迁、不猜**。
6. **严禁的通过手段**：
   - 注释掉报错代码、`try/except: pass` 吞异常；
   - 删除、跳过或弱化既有测试（`skip`/`xfail`/`@Ignore`/`.only` 之外还应检查是否被静默删除）；
   - 放宽类型检查（`any`、`cast`、`# type: ignore`、`eslint-disable`、降低 tsconfig `strict`）；
   - 保留两份实现让「看起来能跑」而不删旧代码。

**出口条件**：所有步骤完成，每步验证通过，无遗留的临时/注释代码。

---

## 阶段 4 · 验收与交付报告

1. 运行**全部**验证：测试、类型检查、lint、构建，并实际启动/跑通关键路径（不只是单测通过）。
2. 运行行数扫描（`scripts/check_file_sizes.py`），确认全部低于阈值；列出最终目录结构与每个文件行数。
3. 静态检查：无循环依赖（`madge --circular` / `jdeps` / 语言等价工具）、无重复定义、无死代码、无未使用 import、无残留的旧路径引用（含文档、配置、脚本、CI 文件中对旧文件的引用）。
4. 输出**交付报告**：
   - 新结构说明；
   - 符号迁移映射表（实际执行结果，与方案对比）；
   - 每个阶段的验证命令与结果；
   - **「拆分前后对外行为等价」声明**：说明依据（测试覆盖范围 + 逐符号核对结果），并如实标注未被测试覆盖的部分；
   - 遗留问题清单（含拆分过程中发现的疑似 bug，明确标注「未修改」）；
   - 行数前后对比表。

---

## 失败处理

| 情况 | 处理 |
|---|---|
| 某步验证失败 | 就地排查修复；若 10 分钟内无法定位，回滚本步到上一个 commit，向用户报告后重新规划该步 |
| 发现方案错误 | 停止，回到阶段 2 更新方案并重新确认 |
| 发现目标文件本身有 bug | **不修**。记录到遗留问题清单，请用户决定是否另开任务 |
| 用户中途改变拆分目标 | 停止当前迁移，回到阶段 1 重新盘点受影响部分 |
